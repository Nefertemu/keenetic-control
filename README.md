# Keenetic Control

Нативное приложение для macOS: WireGuard / AmneziaWG и вся маршрутизация Keenetic
в одном окне. Совмещает возможности Keenetic Config Manager (Windows) и консольного
скрипта `keenetic_fqdn_routes_v17.py`.

Swift + SwiftUI, без единой зависимости: ни Python, ни pexpect, ни PowerShell.

## Запуск

```bash
open "dist/Keenetic Control.app"
```

Приложение можно перетащить в `/Applications` — оно самодостаточное.

## Что умеет

### WireGuard / AmneziaWG
* WireGuard, AmneziaWG и AmneziaWG 2.0 (`Jc/Jmin/Jmax/S1..S4`, `H1..H4`, `I1..I5`);
* загрузка `.conf` кнопкой или перетаскиванием в окно;
* безопасное обновление: бэкап → новый пир **без** AllowedIPs → адреса, MTU, порт,
  обфускация → приватный ключ → AllowedIPs → проверка → удаление старого пира →
  включение → сохранение;
* автоматический откат на rollback-базу, если что-то пошло не так;
* ручной откат последнего обновления;
* переименование туннеля из приложения (подпись `description`, техническое имя `WireguardN` не меняется);
* rollback-база хранится в связке ключей macOS (аналог Windows DPAPI);
* сверка количества маршрутов до и после обновления.

### Ping-Check
* профили проверки связи: узел, режим (ICMP/TCP), интервал, пороги отказа
  и подъёма, тайм-аут;
* создание, изменение и удаление профилей;
* назначение на интерфейсы и флаг перезапуска туннеля при потере связи;
* видно, какой профиль на каком интерфейсе и кто не используется;
* ручная проверка цели через каждый WireGuard-интерфейс: ICMP, TCP-connect или
  UDP-трассировка, с адресом источника и задержкой отдельно для каждого туннеля;
  для TCP/UDP цель должна уже попадать в маршрут выбранного туннеля;
* на экране WireGuard — живая проверка назначенного профиля и статистики
  интерфейса с автообновлением и кнопкой ручной проверки;
* состояние берётся из отдельной команды `show ping-check` (или RCI), поэтому
  `pass`/`fail` и счётчики не путаются с общим статусом интерфейса;
* история здоровья туннеля: график за 24 часа, доступность и список обрывов
  за 7 дней в локальном файле без паролей и конфигурации;
* отдельная «Диагностика»: DNS-резолвинг цели, наличие FQDN/статического
  маршрута и MTU WireGuard с понятными предупреждениями;
* адаптивная таблица с горизонтальной прокруткой — узкие окна не ломают вёрстку;
* **в веб-панели Keenetic этого нет вовсе** — только через командную строку.

Параметры, диапазоны и значения по умолчанию сверены с официальным
справочником команд Keenetic; форма записи проверена на живом роутере.

### Списки доменов
Загрузка и маршруты — две половины одного экрана: сначала «Источники»,
потом «Маршруты». Раньше это были два пункта боковой панели, и экран
загрузки объяснял в тексте, что маршруты назначаются «на другой вкладке».

### Списки FQDN

Вверху раздела **«Списки доменов» → «Обновить списки»** — обновление одним
нажатием. Кнопка доступна на обеих вкладках. Приложение само подключится,
найдёт уже установленные источники, загрузит свежие домены и подсети,
добавит новые записи и удалит исчезнувшие. После завершения покажет итог
по каждому источнику и ссылку на резервную копию.

Части содержат не более **300 записей** (или меньше, если так задано в
настройках). Сначала освобождаются места от исчезнувших записей, затем
заполняются существующие части. Дополнительные части получают ту же цепочку
туннелей, порядок и флаги. Существующие ID и действующие записи не
перераспределяются без необходимости; освободившиеся части сохраняются
для следующего обновления. Например, 601 запись помещается в 300 + 300 + 1.

Свежие источники проверяются целиком: кэш, неполный ответ или нераспознанные
строки не используются для автоматического удаления. Такой источник
пропускается с объяснением, остальные обновляются. Различающиеся маршруты
частей или неоднозначные имена также требуют исправления до обновления.
Ручные списки, не связанные с источником по описанию, остаются без изменений.

Источники загружаются параллельно, не более трёх одновременно. До записи
обновление можно отменить. Если исчезло больше половины списка и не менее
20 записей, приложение показывает отдельное подтверждение с числом удалений.
После подтверждения источник и конфигурация проверяются заново; изменившиеся
данные требуют новой сверки. При отключённом сохранении результат явно
помечается «Применено временно».

Перед записью создаётся защищённая копия. Приложение проверяет полный состав
частей, маршруты и лимиты, после чего сохраняет конфигурацию, если сохранение
включено в настройках. При отсутствии изменений команды и копии не создаются.
Для первого добавления источника остаётся ручной импорт с просмотром плана:

* имена интерфейсов везде показываются вместе с примечаниями из
  конфигурации роутера — «Wireguard0 · Dataforest»;
* восемь готовых источников: hoaxisr, ITDog inside, KinoPub, Telegram, Meta,
  Twitter/X, Twitch, Discord;
* домены и подсети (IPv4 + IPv6) кладутся в одну `object-group fqdn`;
* автоматическая нарезка по частям, нумерация и приведение имён к канону;
* удаление доменов, пропавших из источника;
* кэш источников с настраиваемым временем жизни;
* корректный IDNA/punycode для кириллических доменов;
* ручное создание небольшого списка прямо в приложении (по умолчанию пример `test` с `2ip.io` и `whoer.net`);
* **ручной импорт не меняет маршруты** — их можно назначить на вкладке «Маршруты».

### Разделы
Девять пунктов в трёх группах. «Туннели» — один раздел с
вкладками «Состояние / Обновление / Ping-Check / Диагностика»: они про один и
тот же объект, а наблюдение и опасная замена конфига больше не лежат в одной
прокрутке. «Списки доменов» — «Источники / Маршруты».

### Обзор
Сначала замечания по текущему состоянию: выключенный интерфейс, на который
идут маршруты; маршрут на несуществующий интерфейс; непроходящая проверка
связи; повисшее рукопожатие; списки без маршрута и сверх лимита. Если
замечаний нет — так и сказано.

### Предпросмотр плана
Кроме команд CLI показывается «было → станет» по каждому списку: сколько
доменов и на какие интерфейсы он пойдёт после применения.

### Быстрый переход
* ⌘K — палитра: разделы, роутеры, списки и туннели одним полем поиска;
  переход ничего не меняет на роутере;
* ⌘1…⌘9 — разделы боковой панели.

### Маршруты списков
* назначение `dns-proxy route object-group` на любой интерфейс;
* назначение выбранных списков сразу на несколько интерфейсов в явном порядке
  (например, `Hetzner FIN → Hetzner DE → Infomaniak` для резервирования);
* флаги `auto` и `reject`;
* снятие маршрутов и удаление списков целиком;
* фильтр «нет на интерфейсе» проверяет именно выбранный интерфейс, а не отсутствие
  маршрутов вообще, плюс поиск;
* роутеры выбираются вертикальными вкладками в боковой панели, без скрытого меню со стрелкой;
* у каждого роутера есть отдельная кнопка подключения и чтения конфигурации —
  можно запустить чтение, не переключая активную вкладку.

### Сравнение роутеров
* два роутера рядом: сколько списков и доменов у каждого;
* что есть на эталонном и отсутствует на активном, и наоборот;
* перенос недостающих доменов одной кнопкой — списки сопоставляются по
  описанию, ничего не удаляется;
* работает благодаря тому, что переключение роутера не рвёт связь: оба
  состояния доступны одновременно.

### Статические маршруты
* просмотр, поиск, добавление и удаление;
* IPv4 и IPv6, `default`, комментарии; интерфейс, шлюз или шлюз вместе с интерфейсом;
* выключенные маршруты Keenetic 5 сохраняют своё состояние при импорте, экспорте
  CLI и восстановлении; в поиске они отмечены отдельно и не выбираются как активные;
* импорт из `BAT`, `CMD`, `TXT` (понимает `route -p add … mask …` и строки Keenetic),
  в том числе файлы в кодировке CP866;
* экспорт в BAT для Windows и в команды Keenetic.

### Поиск маршрута

В разделе **«Поиск маршрута»** можно вставить домен, URL, IPv4 или IPv6.
Показываются совпавшие списки и подсети, порядок интерфейсов, `auto`/`reject`
и подходящие статические маршруты. Запрос можно открыть и через ⌘K.
Поиск использует прочитанную конфигурацию без DNS-запросов и изменений роутера.
Политики отдельных устройств и фактическое прохождение трафика требуют
отдельной диагностики; совпадение нескольких правил не выдаётся за однозначный
выбор туннеля.

### Восстановление и перенос копий

В **«Резервных копиях»** можно выбрать конкретные списки и отдельно вернуть
содержимое, цепочки интерфейсов или статические маршруты. Предпросмотр
пересчитывается при изменении выбора. Пустые, ошибочные и распознаваемые
обрезанные копии отклоняются; состояние затрагиваемых объектов повторно
сверяется перед записью. Результат полностью проверяется до сохранения.
Исторические списки больше 300 записей требуют отдельного исправления:
восстановление не меняет их идентификаторы автоматически.

**«Экспорт с паролем»** создаёт переносимую `.kcportable` копию для другого Mac.
Пароль от 12 символов; AES-GCM, случайная соль, PBKDF2-HMAC-SHA256
с 600 000 итераций. Пароль не сохраняется. Импорт проверяет пароль и целостность,
затем сохраняет локальную `.kcbackup` копию с защитой связкой ключей этого Mac.
Импорт сам по себе не меняет роутер.

### История операций

В **«Журнале» → «Операции»** сохраняются последние 100 операций отдельно для
каждого профиля: состав изменений, результат проверки, версия источника,
ошибки и ссылка на копию перед применением. История переживает перезапуск;
прерванная операция помечается отдельно. Поиск и фильтр замечаний помогают
найти проблемное обновление. Незавершённые записи показывают план, а не
подтверждённое состояние роутера. Пароли и приватные ключи команд скрываются,
полная конфигурация в историю не записывается.

### Общее
* ручное применение плана показывает сводку, предупреждения и команды CLI;
  обычное обновление установленных списков выполняется одним нажатием;
* режим «только предпросмотр»;
* зашифрованная AES-GCM резервная копия `running-config` перед каждым изменением;
  ключ хранится в связке ключей macOS, а старые открытые `.txt` копии мигрируют
  в `.kcbackup` только после проверки расшифровки;
* проверка результата после применения — сверяется, что домены и маршруты реально
  легли; для резервирования дополнительно проверяются порядок интерфейсов и флаги
  `auto`/`reject`;
* конфигурация роутера перечитывается сама — раз в минуту и сразу при
  возврате в приложение, так что правки из веб-панели видно без «Обновить»
  (интервал настраивается, 0 — только вручную); фоновое чтение молчит в
  журнале и говорит лишь тогда, когда конфигурация действительно изменилась;
* журнал с фильтрами, дублируется в файл.

## Авторизация веб-панели

Keenetic сменил механизм входа, и на новых прошивках старая схема отвергает
даже верный пароль. Приложение умеет обе:

* **x-ndw4-interactive** — SCRAM на Argon2id и SHA3-512. Пароль на роутер не
  уходит: стороны обмениваются доказательствами знания секрета, а подпись
  сервера проверяется на клиенте, так что подставной роутер не притворится
  настоящим. Схема выбирается автоматически, когда роутер её объявляет.
* **x-ndw2-interactive** — прежняя схема (realm + challenge, MD5/SHA-256).
  Используется как запасная.

В macOS нет ни SHA3, ни Argon2, поэтому в `Sources/KeeneticControl/Crypto`
лежат свои реализации: Keccak-f[1600] по FIPS 202, BLAKE2b по RFC 7693 и
Argon2id по RFC 9106. Все сверены с контрольными примерами стандартов.

## Два способа связи

| | SSH | HTTP RCI |
|---|---|---|
| Как | `/usr/bin/ssh` в настоящем pty | веб-панель роутера |
| Когда | как в консольном скрипте | когда SSH закрыт |
| Плюс | ничего не надо включать в вебе | структурированный JSON, работает через KeenDNS |

Способ выбирается для каждого роутера отдельно в «Роутеры и настройки».
Обе ветки выполняют одни и те же команды Keenetic CLI.

## Пароли

Приоритет — как в консольном скрипте:

1. переменная `KEENETIC_PASSWORD_<АДРЕС>` (адрес заглавными, не-буквы → `_`);
2. переменная `KEENETIC_PASSWORD`;
3. связка ключей macOS (вводится один раз в карточке роутера).

Пароли не хранятся ни в исходниках, ни в файлах настроек.

## Где что лежит

```
~/Library/Application Support/KeeneticControl/
├── routers.json      профили роутеров (без паролей)
├── settings.json     параметры
├── backups/          зашифрованные снимки running-config (`.kcbackup`)
├── cache/            загруженные списки доменов
├── logs/             журнал
├── operations/       история операций по профилям
├── tunnel-health.json история проверок туннелей (только состояния и время)
└── wireguard/        зашифрованные startup-config перед обновлением туннеля
```

Ключ шифрования привязан к связке ключей этого Mac (`ThisDeviceOnly`), поэтому
обычные `.kcbackup` копии открываются на этом Mac. Для переноса используй
экспорт с паролем в `.kcportable`.

## Сборка из исходников

```bash
./build.sh
```

Нужен Xcode (макросы SwiftUI живут в нём, а не в Command Line Tools). Скрипт сам
подставит `DEVELOPER_DIR`, менять `xcode-select` не требуется.

Сборка подписывается первым найденным сертификатом для подписи кода — например
тем, что Xcode заводит для разработчика. Это важно не для доверия, а для связки
ключей: ад-хок подпись даёт требование вида `cdhash`, оно меняется с каждой
сборкой, и macOS каждый раз заново спрашивает доступ к сохранённым паролям.
Подпись сертификатом привязана к идентификатору бандла и переживает пересборку.
Свой сертификат можно указать явно:

```bash
KC_SIGN_IDENTITY="Apple Development: ..." ./build.sh
```

Сертификата нет — скрипт честно подпишет ад-хок и предупредит.

## Проверка

```bash
./Tools/test.sh

# Отдельные сценарии:
./Tools/test.sh --filter RegressionTests/testWireGuard
./Tools/test.sh --filter RouterConnectionTests
./Tools/test.sh --filter RouterPlanTests
./Tools/test.sh --filter UIRegressionTests
./Tools/test.sh --filter OutcomeSheetTests
./Tools/test.sh --filter DomainListUpdateControllerTests
./Tools/test.sh --filter DomainListSyncPlannerTests
./Tools/test.sh --filter DomainListUpdateUITests
./Tools/test.sh --filter RestoreSafetyTests
./Tools/test.sh --filter PortableBackupTests
./Tools/test.sh --filter RouteExplanation
./Tools/test.sh --filter OperationHistory
```

Проверяются: punycode, нормализация доменов, разбор `running-config` (в том
числе с CRLF, как отдаёт RCI), живое состояние интерфейсов (проверка связи и
рукопожатия WireGuard), разбор CLI/RCI-ответа Ping-Check и диагностика DNS,
маршрутов и MTU, совместимость файла настроек со старыми версиями,
возврат по резервной копии, свои источники, имена интерфейсов и их сворачивание
в сводку, имена файлов резервных копий, статические маршруты, импорт и экспорт BAT, WireGuard
(разбор `.conf` и порядок команд), планировщик, детектор ошибок CLI, обработка
обрыва SSH и криптография схемы x-ndw4 — SHA3-512, HMAC-SHA3-512, BLAKE2b и
Argon2id сверяются с контрольными примерами FIPS 202, RFC 4231, RFC 7693 и
RFC 9106; строгая проверка порядка и флагов failover-маршрутов, безопасное
отбрасывание частичной загрузки подсетей, ошибки битого JSON RCI и AES-GCM
контейнеры резервных копий. С `SELFTEST_NETWORK=1` дополнительно скачиваются
все восемь источников.

Тесты — стандартный target Swift Package (`swift test`). Скрипт выбирает полный
Xcode, если активны только Command Line Tools, и размещает временную сборку
в `~/Library/Caches/KeeneticControl/SwiftPM/`, чтобы File Provider в Desktop
не мешал подписи тестов. Можно указать `--scratch-path` или `KC_TEST_BUILD_DIR`.
Требуются macOS 14+ и Xcode;
UI-проверки создают временные окна SwiftUI в графической сессии macOS.

`RegressionTests` сохраняет все 417 проверок прежнего самотеста. Транспортные
тесты используют подставные соединения и управляемые задержки: отмена ожидания,
смена роутера и адреса, повторное подключение, запрет повторной записи,
резервное копирование и сохранение проверяются без настоящего роутера.
Проверяются поздние ответы после отмены и тайм-аута, свежесть копии перед записью,
исключение посторонних команд между этапами обновления WireGuard, восстановление
порядка резервирования и строгий импорт BAT. Отдельные сценарии проверяют
устаревшие результаты диагностики и фоновой сверки источников.
Настройки, кэш и журнал XCTest находятся во временной папке процесса.

Обновление доменных списков проверяется на границах 300/301/600/601 записей,
повторном запуске, освобождении и повторном использовании частей. Подставной
роутер контролирует лимит после каждой команды. Проверяются наследование
маршрутов, сбои отдельных источников, смена роутера и каталога во время загрузки,
изменение конфигурации перед записью и отказ сохранять непроверенный результат.

`UIRegressionTests` отрисовывает настоящие экраны обзора, доменных и статических
маршрутов, Ping-Check, диагностики и состояния туннелей: 500 маршрутов, 80 списков,
12 интерфейсов, длинные имена и два баннера одновременно.
Проверяются светлая и тёмная темы, ширина области
содержимого 788 и 1220 точек. Проверки измеряют границы блоков, распознают
видимые кнопки баннеров встроенным Vision и проверяют прокрутку длинной таблицы.
`OutcomeSheetTests` проверяет окно результата со 100 длинными ошибками:
список прокручивается, кнопка закрытия остаётся видимой.
`DomainListUpdateUITests` проверяет кнопку обновления, ход загрузки и отчёт
по 20 источникам вместе с баннерами и установленными маршрутами. Автоматические сетевые
чтения экранов отключены только в тестовой среде; используются искусственные данные.
PNG сохраняются в `.build/ui-snapshots/`; в CI они прикладываются к запуску.
Это проверки геометрии и содержимого снимков, без хрупкого побитового сравнения
шрифтов разных версий macOS. Внешние источники проверяются отдельно:
`SELFTEST_NETWORK=1 ./Tools/test.sh --filter RegressionTests/testLiveSourceDownloads`.
Строгая загрузка для однокнопочного обновления:
`KC_LIVE_DOMAIN_SOURCES=1 ./Tools/test.sh --filter StrictSourceLoaderTests/testLiveCatalogSourcesAreFreshAndComplete`.

`RouterSession` связывает состояние с SwiftUI. `RouterConnectionManager`
владеет пулом соединений и поколениями операций; `RouterPlanExecutor` выполняет
резервное копирование, команды, сохранение и проверку результата. Зависимости
транспорта, пароля, повторных попыток и копий передаются через
`RouterSessionDependencies`.

Дополнительные проверки покрывают hosts-алиасы и мусор в источниках, лимит
300 при старых настройках, отмену чтения и загрузки, подтверждение резкого
сокращения, повреждённые копии, устаревшее восстановление, тихо проигнорированные
команды, переносимую криптографию и сохранность истории после перезапуска.
UI-сценарии нажимают настоящие кнопки обновления, отмены и закрытия, проверяют
выборочное восстановление и поиск маршрута в обеих темах.

Workflow «Доступность источников» отдельно проверяет свежие полные списки
каждый понедельник и по ручному запуску. Релизная сборка берёт код из указанного
существующего тега и проверяет соответствие коммита и версии приложения.
